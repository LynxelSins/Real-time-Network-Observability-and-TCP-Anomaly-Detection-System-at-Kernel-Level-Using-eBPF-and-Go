ในร่างเค้าโครงฉบับปัจจุบัน (Ass6_เค้าโครงโครงงานSeminar_ร่างที่1.pdf) การวิเคราะห์ข้อมูลสำรวจ (EDA) บนข้อมูลเครือข่ายจริง และตารางวัดประสิทธิภาพโมเดล/ระบบ (Performance Evaluation Matrix) ยังคงขาดหายไป 100% โดยถูกจัดอยู่ในสถานะ "ยังไม่ทำ" ในตารางที่ 3 (หน้า 7–8)

หากต้องการยกระดับโครงงานนี้จากข้อเสนอเชิงหลักการไปสู่ Empirical Computer Engineering Project ที่พร้อมรับการอนุมัติ นักศึกษาจำเป็นต้องเพิ่ม 2 ส่วนนี้เข้าสู่เล่มข้อเสนอ ดังนี้:

1. สิ่งที่ขาดหายไปในส่วน EDA (Exploratory Data Analysis on Real Traffic Data)
ในรายงานปัจจุบัน สภาพแวดล้อมการทดสอบใช้เพียงสคริปต์วนลูปคำสั่ง curl แบบสังเคราะห์เบื้องต้น ยังขาดการนำเสนอพฤติกรรมข้อมูลทราฟฟิกเครือข่ายจริง (Real/Captured TCP Data Traces) ดังนี้:

ชุดข้อมูลอ้างอิง (Dataset/PCAP Source): ยังไม่ได้ระบุว่าใช้ชุดข้อมูลเปิดมาตรฐาน (เช่น CAIDA, MAWI Wireless Traces) หรือชุดข้อมูลที่ดักจับเองจาก LAN ภายในห้องปฏิบัติการ (24-Hour Network Trace PCAP)
กราฟและสถิติการกระจายตัวของสตรีมเครือข่าย (Traffic Distribution Plots):
Handshake Latency Distribution: กราฟการกระจายตัวของเวลาการเชื่อมต่อ SYN \to ESTABLISHED ในสภาวะปกติ เพื่อหาค่าเปอร์เซ็นไทล์ (P_{50}, P_{90}, P_{99}) สำหรับตั้งค่า Threshold
Retransmission Rate Baseline: อัตราส่วนแพ็กเก็ตส่งซ้ำเฉลี่ยต่อช่วงเวลาปกติ เทียบกับช่วงที่มีสภาวะ Network Congestion
Connection Lifetime & Flow Volume: การกระจายตัวของอายุการเชื่อมต่อ (Duration) และปริมาณ Active Sockets พร้อมกันในระบบ
Incomplete Handshake Ratio: อัตราส่วนระหว่าง SYN-SENT กับ ESTABLISHED เพื่อใช้จำแนกพฤติกรรมปกติออกจาก SYN Flood

จากการตรวจสอบเอกสารเค้าโครงโครงงานเรื่อง "ระบบตรวจสอบสภาวะเครือข่ายแบบเรียลไทม์และการตรวจจับสิ่งผิดปกติของโปรโตคอล TCP ในระดับเคอร์เนลด้วย eBPF และภาษา Go" (Ass6_เค้าโครงโครงงานSeminar_ร่างที่1.pdf) ของนักศึกษา (นายเมธัส มณีวิจิตร และ นางสาวปภาวรินทร์ นาเมืองรักษ์)

เมื่อนำมาประเมินเทียบกับ กรอบมาตรฐานสถาปัตยกรรม eBPF Network Observability (Project 1) ที่เราเคยกำหนดไว้ พบว่าตัวเล่มมีรากฐานเบื้องต้นที่ดีมาก (มีการทำ Toy Model ที่ดักจับ Tracepoint sock/inet_sock_set_state และ tcp/tcp_retransmit_skb อ่านผ่าน BPF Ring Buffer เข้าสู่ Go Consumer ได้จริงแล้ว)

อย่างไรก็ตาม ยังมีส่วนสำคัญทางวิศวกรรมคอมพิวเตอร์และธรรมาภิบาลระบบ (System & Security Governance) อีก 6 ประเด็นหลักที่ยังขาดหายไป ซึ่งจำเป็นต้องให้นักศึกษาเติมเต็มก่อนเข้าสู่ระยะพัฒนาฉบับสมบูรณ์:

1. กลไกตรวจจับข้อมูลสูญหาย (Drop Counters & Event Loss Telemetry)
สิ่งที่รายงานระบุ: ในหัวข้อ 6.7 เขียนไว้เพียงว่าเป็นข้อจำกัดว่า "Ring Buffer มีขนาดจำกัด หากปริมาณ Event สูงมากอาจมี Event ถูกทิ้ง"
สิ่งที่ขาดหายไป: การระบุเป็นข้อจำกัดยังไม่เพียงพอต่อระบบ Observability ระดับ Production ระบบต้องมี Drop Counter Mechanism ในฝั่ง Go Agent ที่คอยฟัง Callback สัญญาณ RingBuffer.LostSamples หรือ BPF Loss Metrics เพื่อแจ้งเตือนบน Dashboard ให้ผู้ดูแลระบบทราบทันทีเมื่อเกิดเหตุการณ์ "ข้อมูลสตรีมมิ่งหลุดรอด" (Data Loss under High Traffic)
2. การบริหารจัดการหน่วยความจำเคอร์เนล (LRU Map vs Standard Hash Map)
สิ่งที่รายงานระบุ: ปัจจุบันใช้ BPF Hash Map ขนาดสูงสุด 10,240 รายการ และเขียนหมายเหตุไว้ว่าจะพิจารณาเปลี่ยนเป็น LRU Hash Map ในอนาคต
สิ่งที่ขาดหายไป: BPF Hash Map แบบดั้งเดิมมีความเสี่ยงสูงที่จะเกิด Memory Exhaustion (ตารางเต็ม) หากเครือข่ายเผชิญการเชื่อมต่อสั้นๆ จำนวนมหาศาล (Connection Churn) หรือ SYN Flood การใช้ LRU Hash Map (Least Recently Used) เป็นเงื่อนไขบังคับเชิงสถาปัตยกรรมเพื่อรับประกันว่าเคอร์เนลจะไม่ปฏิเสธการเขียนข้อมูลใหม่ และป้องกันไม่ให้เกิด Memory Leak ใน Kernel Space
3. กรอบความสอดคล้องทางกฎหมายและธรรมาภิบาลข้อมูล (PDPA & Computer Crime Act Compliance)
สิ่งที่รายงานระบุ: ยังไม่มีการกล่าวถึงมิติด้านความปลอดภัย ข้อมูลส่วนบุคคล หรือข้อกำหนดทางกฎหมายเลย
สิ่งที่ขาดหายไป: การใช้ eBPF เข้าไปดักจับ IP Address, Port และ TCP State ในระดับเคอร์เนล ถือเป็นกลไกการเข้าถึงข้อมูลระบบ (System/Flow Interception) ตาม พ.ร.บ. คอมพิวเตอร์ฯ (มาตรา 7, 8) และกฎหมาย PDPA โครงงานต้องเพิ่มส่วน Compliance & Access Governance เช่น:
การไม่ดักจับหรือจัดเก็บ Payload ของผู้ใช้ (Header/Flow-level Only)
การจัดเก็บ Log ในรูปแบบ Masked/Hashed IP Address สำหรับรายงานสาธารณะ
การสร้าง Audit Log สำหรับตัวโปรแกรม eBPF เอง
4. ชุดทดสอบสภาวะวิกฤตเชิงปริมาณ (Systematic Benchmark Harness: hping3 & tc)
สิ่งที่รายงานระบุ: สคริปต์ทดสอบปัจจุบันใช้เพียง curl และการยิงไปยัง IP ที่ไม่ตอบสนอง และวางแผนจะใช้ tc netem ในอนาคต
สิ่งที่ขาดหายไป: ขาดการกำหนดสคริปต์จำลองการโจมตีจริง เช่น การใช้ hping3 ทำ SYN Flood เพื่อทดสอบเกณฑ์ขีดจำกัด (Break-point) ของระบบ และขาดตัวชี้วัดเชิงเปรียบเทียบ (Quantitative Metrics) เช่น:
Detection Latency: ความหน่วงตั้งแต่เกิด Anomaly จนถึงการแจ้งเตือน (ต้อง < 500ms)
Throughput Capacity: อัตราปักหมวดแพ็กเก็ตสูงสุดที่รับได้ก่อน Ring Buffer จะ overflow (Packets/Sec)
5. สถาปัตยกรรมแสดงผลแบบเรียลไทม์ (Web-Based Real-time Dashboard)
สิ่งที่รายงานระบุ: ปัจจุบันแสดงผลผ่าน Terminal หน้าจอข้อความธรรมดา
สิ่งที่ขาดหายไป: ขาดสถาปัตยกรรมเชื่อมโยงข้อมูลจาก Go Agent ไปยัง Web Interface (เช่น WebSocket Server + React/Tailwind UI หรือ Grafana Integration) เพื่อให้เห็นกราฟสภาวะ TCP State Transition และ Retransmission Spikes แบบเรียลไทม์ตามเป้าหมายวัตถุประสงค์ข้อ 3.3
6. กลยุทธ์การพกพาและข้ามเคอร์เนล (Libbpf CO-RE & Kernel Portability Strategy)
สิ่งที่รายงานระบุ: ล็อกสภาพแวดล้อมไว้เฉพาะ Fedora Linux 44 (Kernel 7.2.7) เท่านั้น
สิ่งที่ขาดหายไป: โครงงาน eBPF ที่ได้มาตรฐานวิศวกรรมควรใช้ Libbpf CO-RE (Compile Once – Run Everywhere) ผ่าน vmlinux.h และ BTF เพื่อให้ไบนารี Go + eBPF สามารถนำไปรันบน Linux Kernel เวอร์ชันอื่น (เช่น 5.15+ หรือ 6.x) ได้โดยไม่ต้อง Recompile ซอร์สโค้ดใหม่ทุกครั้ง
📝 สรุปข้อแนะนำเพื่อให้นักศึกษานำไปปรับปรุงในระยะถัดไป
เพิ่มโมดูล Drop Counter ในโค้ด Go Agent เพื่ออ่านและรายงานจำนวน Lost Events
เปลี่ยน BPF Map เป็น LRU Hash Map เพื่อความปลอดภัยของหน่วยความจำเคอร์เนล
เพิ่มสคริปต์ hping3 ในชุดทดสอบเพื่อวัด Detection Rate และ CPU Overhead (<5%) ภายใต้สภาวะ SYN Flood
เพิ่มหัวข้อ PDPA & CCA Compliance ในส่วนขอบเขตและความปลอดภัยของระบบ
ต่อยอด Go WebSocket API เพื่อส่งข้อมูลไปยัง Web Dashboard

สรุปผลการทำ Step 1.1: ปรับปรุง eBPF C (
tcp_monitor.bpf.c
)
สิ่งที่ทำเสร็จแล้ว:

เปลี่ยนชนิด Map จาก Hash ธรรมดา เป็น BPF_MAP_TYPE_LRU_HASH:
แก้ปัญหา Memory leak และ Map เต็มเมื่อเจอ SYN Flood หรือ Half-open connection (Kernel จะเคลียร์ Socket ที่เก่าสุดทิ้งให้อัตโนมัติ)
เพิ่ม BPF Array Map drop_counters:
ทำ Drop Counter ระดับ Kernel สำหรับนับ Event ที่ส่งเข้า Ring Buffer ไม่ทันเมื่อ Buffer เต็ม (แยกนับทั้ง State Change และ Retransmit)
ปรับปรุงการดักจับ Incomplete Handshake:
บันทึก Duration แม้ว่า Socket จะถูก Reset/Closed ก่อนที่จะไปถึงสถานะ TCP_ESTABLISHED
Compile & Generate Go Bindings สำเร็จ:
รัน go generate ผ่านเรียบร้อย ได้ bindings ชุดใหม่พร้อมใช้งานในภาษา Go

สรุปผลการทำ Step 1.2: ปรับปรุง Go eBPF Reader & Drop Counter
สิ่งที่ทำเสร็จแล้ว:

แยกโมดูล
reader.go
:
สร้าง Struct TCPEvent ระดับ User Space ที่เก็บข้อมูลพร้อมใช้ (Timestamp, IPs, Ports, Duration, State Names, Process)
รองรับการแปลง Raw Bytes จาก Ring Buffer อย่างเป็นระเบียบ
ระบบนับสถิติและ Drop Counters:
ดึงสถิติจาก BPF Map drop_counters ในเคอร์เนล (KernelStateDrops, KernelRetransDrops) มาแสดงผล
ติดตามสถานะ Incomplete Handshake อัตโนมัติเมื่อ Socket ถูกปิด/รีเซ็ตก่อนถึงสถานะ ESTABLISHED
ปรับปรุง
main.go
:
เปลี่ยนมาใช้ NewEventReader
เมื่อโปรแกรมจบการทำงาน (กด Ctrl+C) จะสรุปจำนวน Events ทั้งหมด และจำนวน Drops ที่เกิดขึ้นให้ทันที
ทดสอบ Build สำเร็จ:
รัน go build -o tcp_monitor . ผ่านเรียบร้อย ไบนารีพร้อมทำงาน

สรุปผลการทำ Step 2.1: Anomaly Detection Engine (
detector.go

ตรวจจับได้ทันทีจาก Event Retransmission
Port Scanning (การสแกนพอร์ต เช่น ใช้ nmap -sT หรือ nmap -sS):
Hacker มักจะสแกนพอร์ตที่ไม่ได้เปิด ทำให้เกิด Incomplete Handshake หรือโดน RST/CLOSE รัว ๆ
TCP SYN Flood DoS / DDoS (การยิงถล่มเซิร์ฟเวอร์ด้วย SYN):
ตรวจจับได้จากอัตรา Incomplete Handshake พุ่งสูงผิดปกติในเวลาสั้น ๆ

สิ่งที่ทำได้เลยตอนนี้ (Detection & Alert):

รู้ตัวทันที เมื่อมีคนยิง SYN Flood เข้ามา หรือมีคนพยายามสแกนพอร์ต
รู้ว่าใครยิง: เห็น Source IP, Port, Process ที่เกี่ยวข้อง และเวลาที่เริ่มโดนยิง
ระบบมอนิเตอร์ไม่พัง: เพราะเราเปลี่ยน BPF Map เป็น LRU_HASH ทำให้เวลาโดนยิงถล่ม Map ของ eBPF จะไม่ล้นและ Kernel จะไม่ค้าง
ถ้าอยากให้ "กัน/บล็อก" ได้ด้วย ต้องทำอย่างไร?

ปัจจุบันเราดักที่ Tracepoint (sock/inet_sock_set_state และ tcp_retransmit_skb) ซึ่ง Tracepoint ในเคอร์เนลมีคุณสมบัติเป็น Read-only (อ่านได้อย่างเดียว ห้ามดัดแปลงหรือดรอปแพ็กเก็ต)
ถ้าต้องการ "กันคนยิง (Mitigation/Drop)": ต้องเขียนโปรแกรม eBPF อีกตัวหนึ่งประเภท XDP (eXpress Data Path) หรือ tc (Traffic Control) ไปดักที่ Network Interface Card (NIC) โดยตรวจว่าถ้า IP ไหนมีพฤติกรรม SYN Flood ให้สั่ง XDP_DROP ทิ้งที่ระดับ Driver ทันที ก่อนที่แพ็กเก็ตจะวิ่งเข้าถึง Kernel TCP Stack
กันคนแฮก (Application Exploits / Web Attacks) ได้ไหม?

กันไม่ได้ เช่น SQL Injection, Cross-Site Scripting (XSS), หรือการเจาะรหัสผ่าน เพราะการแฮกพวกนั้นเป็นการส่งโค้ดอันตรายมาในระดับ Application Payload (HTTP / L7) แต่ตัวมอนิเตอร์ของเราดูเฉพาะ TCP Header & Connection Behavior (L4)

import json

def load_alerts(jsonl_path):
    records = []
    if not os.path.exists(jsonl_path):
        print(f"❌ ไม่พบไฟล์ log: {jsonl_path}")
        return pd.DataFrame()

    with open(jsonl_path, 'r', encoding='utf-8') as f:
        for line in f:
            line = line.strip()
            if line:
                try:
                    records.append(json.loads(line))
                except json.JSONDecodeError:
                    continue

    df = pd.DataFrame(records)
    if not df.empty and 'timestamp' in df.columns:
        df['dt'] = pd.to_datetime(df['timestamp'])
    return df

def calculate_metrics(alerts_df, timeline_csv_path):
    print("=" * 60)
    print("  📊 การประเมินประสิทธิภาพการตรวจจับ (Detection Performance)")

    if not os.path.exists(timeline_csv_path):

    print("Ground Truth Phases:")
    for _, row in timeline_df.iterrows():

        for atype, cnt in type_counts.items():

    print("\n" + "=" * 60)

def generate_eda_report(alerts_df, out_dir):
    print("📈 กำลังประมวลผลสถิติและทำ EDA...")
    os.makedirs(out_dir, exist_ok=True)

    summary_file = os.path.join(out_dir, "eda_summary.txt")
    with open(summary_file, 'w', encoding='utf-8') as f:
        f.write("=== eBPF TCP Anomaly Detection EDA Summary ===\n\n")
        f.write(f"Generated at: {datetime.now().isoformat()}\n")
        f.write(f"Total Anomalies Logged: {len(alerts_df)}\n\n")

        if not alerts_df.empty and 'duration_ms' in alerts_df.columns:

                f.write("Latency Statistics (ms):\n")

                f.write(f"  StdDev: {durations.std():.2f} ms\n")

                f.write(f"  Max:    {durations.max():.2f} ms\n")
                f.write(f"  95th %: {durations.quantile(0.95):.2f} ms\n")
                f.write(f"  99th %: {durations.quantile(0.99):.2f} ms\n")

    print(f"✔ บันทึกบทสรุปสถิติที่: {summary_file}")

    # พยายามนำเข้า matplotlib สำหรับวาดรูป (ถ้าติดตั้งไว้)

        if not alerts_df.empty and 'duration_ms' in alerts_df.columns:
            latencies = alerts_df[alerts_df['duration_ms'] > 0]['duration_ms'].dropna()

            if len(latencies) > 0:
                plt.figure(figsize=(10, 5))

                # กราฟที่ 1: Latency Distribution (Histogram + CDF)
                plt.subplot(1, 2, 1)
                sorted_data = np.sort(latencies)

                plt.title("Handshake Latency CDF")

1. สรุปภาพรวมการทำงานของระบบ (System Architecture Overview)
ระบบแบ่งออกเป็น 4 เลเยอร์หลัก:

Kernel Space Layer (eBPF in C):

เกาะติดกับ Kernel TCP Stack ผ่าน 2 Tracepoints:
sock/inet_sock_set_state: ดักจับการเปลี่ยนสถานะของ TCP เช่น SYN_SENT, ESTABLISHED, CLOSE
tcp/tcp_retransmit_skb: ดักจับเมื่อ Kernel ส่งแพ็กเก็ตซ้ำ (Retransmission)
ใช้ BPF LRU Hash Map (sock_store) จำ Timestamp เมื่อเริ่มส่ง SYN เพื่อคำนวณ Handshake Latency หรือ Connection Duration โดย Kernel จะเคลียร์ข้อมูลเก่าทิ้งเองอัตโนมัติหากเจอการโจมตี SYN Flood
ส่งข้อมูลขนาดกะทัดรัดขึ้น User Space ผ่าน BPF Ring Buffer (events) พร้อมทั้งมี BPF Array Map (drop_counters) สำหรับบันทึกว่ามี Event ตกหล่นกี่ตัวในกรณีที่ Ring Buffer เต็ม
Data Ingestion & Extraction Layer (Go Userspace - reader.go):

อ่านข้อมูลดิบจาก Ring Buffer แปลงเป็น TCPEvent ระดับ High-level (ดึง IP, Port, Process Name, State Transition, Duration)
ดึงค่า Drop Counters จาก Kernel มาตรวจสอบความสมบูรณ์ของข้อมูลแบบ Real-time
ดักจับสถานะ Incomplete Handshake (กรณี Connection ถูก Reset หรือปิดก่อนที่จะเป็น ESTABLISHED)
Detection & Dispatching Engine (detector.go & logger.go):
